# Diagnóstico da CA TLS para acesso local à FNRH

Data: 29/08/2026
Escopo: inspeção de certificados e testes `GET` sem credenciais, sem alteração do processo operacional, do código ou da configuração do projeto.

Ambiente inspecionado:

| Item | Valor |

| Plataforma | `win32` |

Nesta versão, `node --help` confirma suporte a:

- `--use-bundled-ca`, padrão atual;
- `--use-openssl-ca`;

O Node padrão usa o bundle incorporado, não a confiança do Windows. A documentação oficial do Node `v22.18.0` confirma que `NODE_EXTRA_CA_CERTS` estende as CAs conhecidas e só é lido durante a inicialização do processo. A mesma versão oferece `tls.getCACertificates()` para distinguir certificados `bundled`, `system`, `extra` e `default`: <https://nodejs.org/download/release/v22.18.0/docs/api/cli.html#node_extra_ca_certsfile> e <https://nodejs.org/download/release/v22.18.0/docs/api/tls.html#tlsgetcacertificatestype>.

## 2. Cadeia TLS apresentada pela FNRH

A conexão observada nesta máquina é interceptada pelo HTTPS scanning do Avast. Portanto, o Node local não recebe diretamente o certificado público original do domínio.

O OpenSSL do Git for Windows observou exatamente **um** certificado apresentado:

| Campo | Valor |
|---|---|
| Subject | `CN=fnrh.turismo.serpro.gov.br` |
| Issuer | `CN=Avast Web/Mail Shield Root, O=Avast Web/Mail Shield, OU=generated by Avast Antivirus for SSL/TLS scanning` |
| Validade inicial | `2026-07-23T12:06:49Z` |
| Validade final | `2026-10-21T12:06:48Z` |
| SHA-256 do leaf | `3C:ED:D2:69:76:F2:E9:40:37:4A:D6:23:8A:8A:C5:8D:44:69:A2:4D:C9:45:03:E4:1F:2F:CC:A0:EA:06:23:09` |

O servidor/interceptador não enviou a raiz Avast, o que é normal para uma raiz de confiança. O problema é que o bundle padrão do Node não contém essa CA privada.

Resultado da validação padrão:

```text
Verification error: unable to verify the first certificate
Verify return code: 21
Node: UNABLE_TO_VERIFY_LEAF_SIGNATURE
```

A documentação oficial do Avast confirma que seu Web Guard realiza HTTPS scanning e que essa funcionalidade é habilitada por padrão: <https://support.avast.com/en-uk/article/use-antivirus-https-scan>.

A cadeia pública real do domínio ficou encoberta pela interceptação local e não deve ser inferida a partir do leaf Avast. O SERPRO publica oficialmente cadeias SSL próprias, incluindo “Autoridade Certificadora Raiz Brasileira v10” e “Autoridade Certificadora do SERPRO SSL”, mas não foi possível provar neste ambiente que essa é exatamente a cadeia atualmente servida por este hostname fora da interceptação: <https://www.serpro.gov.br/links-fixos-superiores/pss-serpro/acserprossl>.

## 3. Certificado/CA problemático

A CA ausente do bundle padrão do Node e necessária para validar a conexão **como ela é apresentada nesta máquina** é:

| Campo | Valor |
|---|---|
| Subject | `CN=Avast Web/Mail Shield Root, O=Avast Web/Mail Shield, OU=generated by Avast Antivirus for SSL/TLS scanning` |
| Issuer | igual ao Subject; raiz autoassinada |
| Função | CA raiz privada do HTTPS scanning do Avast |
| Validade inicial | `2010-01-01T12:00:00Z` |
| Validade final | `2040-01-01T12:00:00Z` |
| SHA-256 | `53:0B:F9:30:17:B0:90:33:62:1F:B6:87:09:7E:23:F0:F4:A7:35:A9:80:EF:C3:55:BC:C0:A1:76:77:9E:58:69` |
| SHA-1/Thumbprint Windows | `7D721575A097FEB5B6A08F6BAB43B12A997F43BC` |
| Serial | `436F068D41F3AB4F81D141C51CC0C693` |
| Basic Constraints | CA habilitada, sem limite de caminho |
| Key Usage | assinatura de certificado e CRL |

Ela está instalada em:

- `Cert:\CurrentUser\Root`;
- `Cert:\LocalMachine\Root`.

As duas cópias têm o mesmo fingerprint. A origem confiável para um eventual PEM é o próprio Windows Certificate Store desta instalação, depois de conferir o fingerprint acima. Não se deve baixar essa raiz de site aleatório.

## 4. Windows trust store vs Node

O Windows confia na raiz Avast porque ela está nos repositórios de autoridades raiz confiáveis. O Node `v22.18.0` consegue enumerá-la por `tls.getCACertificates("system")`, mas não a inclui em `tls.getCACertificates("default")` enquanto iniciado no modo padrão.

Isso explica integralmente a diferença:

```text
Windows/navegador → confia na raiz Avast → valida o leaf substituto
Node padrão       → bundle incorporado sem a raiz Avast → UNABLE_TO_VERIFY_LEAF_SIGNATURE
```

Com `--use-system-ca`, o Node passa a combinar a confiança do sistema com seu conjunto padrão. O teste confirmou que a raiz de fingerprint `53:0B:...:58:69` é encontrada pelo Node no conjunto `system`.

## 7. CA recomendada

Para a conexão interceptada nesta máquina, o certificado exato para um arquivo `NODE_EXTRA_CA_CERTS` é a raiz **Avast Web/Mail Shield Root**, com SHA-256:

```text
53:0B:F9:30:17:B0:90:33:62:1F:B6:87:09:7E:23:F0:F4:A7:35:A9:80:EF:C3:55:BC:C0:A1:76:77:9E:58:69
```

Não se deve adicionar:

- o leaf temporário de `fnrh.turismo.serpro.gov.br`;
- chave privada;
- certificado coletado de fonte aleatória;
- uma cadeia SERPRO por suposição, pois ela não é a cadeia que o Node local está recebendo enquanto o Avast intercepta.

Apesar de a raiz Avast ser a CA correta para `NODE_EXTRA_CA_CERTS`, a recomendação operacional principal é usar `node --use-system-ca server.js`. Isso evita manter uma cópia estática da raiz privada e acompanha eventual rotação feita pelo Avast no Windows.

## 8. Teste com `NODE_EXTRA_CA_CERTS`

Procedimento controlado:

1. a raiz Avast foi localizada pelo thumbprint no `CurrentUser\Root`;
2. foi exportada para DER num diretório aleatório em `%TEMP%`;
3. foi convertida para PEM pelo OpenSSL do Git;
4. subject, issuer, validade e fingerprint foram reconferidos;
5. um novo processo Node foi iniciado com `NODE_EXTRA_CA_CERTS` apontando para esse PEM;
6. `NODE_TLS_REJECT_UNAUTHORIZED` foi explicitamente removido do ambiente do teste;
7. foi feito somente um GET sem credenciais;
8. o diretório temporário foi validado como descendente de `%TEMP%` e removido ao final.

Nenhum certificado foi salvo no repositório.

## 9. Resultado

Resultados comparativos:

| Configuração | TLS | HTTP alcançado |
|---|---|---|
| Node padrão | falhou: `UNABLE_TO_VERIFY_LEAF_SIGNATURE` | não |
| `node --use-system-ca` | passou | sim, HTTP `401` sem credenciais |
| `NODE_EXTRA_CA_CERTS=<raiz Avast temporária>` | passou | sim, HTTP `401` sem credenciais |

O HTTP `401` é o resultado esperado e suficiente: comprova que o handshake TLS terminou e que a API passou a exigir autenticação. Nenhuma credencial foi enviada e nenhum corpo com dados pessoais foi consultado.

O arquivo temporário foi removido com sucesso.

## 10. Configuração definitiva recomendada

Opção preferida para esta máquina e versão do Node:

```bat
node --use-system-ca server.js
```

Vantagens:

- usa a mesma raiz Avast já confiada pelo Windows;
- preserva validação TLS;
- não exporta nem duplica certificado;
- acompanha atualização/rotação do certificado feita pelo software que administra a trust store;
- o teste real de handshake já passou.

Alternativa com CA explícita, caso se deseje limitar a mudança ao mecanismo originalmente proposto:

```bat
set "NODE_EXTRA_CA_CERTS=C:\ProgramData\VivaMar\certs\avast-web-mail-shield-root.pem"
node server.js
```

Nesse caso, o PEM deve ser exportado da trust store local, conferido pelo fingerprint, mantido fora do Git e substituído quando o Avast rotacionar sua raiz.

As duas opções ampliam a confiança TLS do processo inteiro, não apenas do hostname FNRH. A escolha deve ser registrada como decisão operacional consciente.

## 11. Impacto no `start-local.bat`

Uma mudança futura mínima seria substituir a última linha por:

```bat
node --use-system-ca server.js
```

Nenhuma mudança em `backend/server.js` ou `.env` seria necessária.

Se a alternativa PEM for escolhida, o BAT deverá:

- definir caminho absoluto estável antes de iniciar o Node;
- verificar que o arquivo existe;
- falhar de forma explícita se estiver ausente;
- nunca definir `NODE_TLS_REJECT_UNAUTHORIZED=0`.

`NODE_EXTRA_CA_CERTS` não deve depender do `dotenv`, pois o Node lê essa variável somente ao iniciar o processo.

## 12. Considerações sobre Render

O certificado Avast é exclusivo da interceptação HTTPS local. Ele não deve ser enviado ao Render nem adicionado às variáveis do backend hospedado.

No Render, a conexão deve receber a cadeia pública real do domínio. Se o backend hospedado não apresenta erro TLS, nenhuma mudança é indicada. Se apresentar, deve-se coletar a cadeia diretamente naquele ambiente e usar somente a CA pública oficial correspondente, não a raiz Avast.

## 13. Riscos

- Confiar na raiz Avast permite que o antivírus inspecione conexões TLS feitas por esse processo Node, assim como já ocorre com aplicações que usam a trust store do Windows.
- Um PEM estático pode expirar, ficar obsoleto ou deixar de corresponder à raiz após atualização do Avast.
- Adicionar o leaf temporário criaria uma configuração frágil, com expiração em 21/10/2026.
- Desabilitar validação TLS permitiria interceptação não autenticada e é inaceitável.
- Desativar globalmente o HTTPS scanning do Avast reduziria proteção do equipamento; não foi feito nem recomendado como primeira opção.
- A cadeia pública real da FNRH pode mudar independentemente da raiz local do Avast.
